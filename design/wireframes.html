01 · Структура системы

Три подсистемы поверх одного API и одной БД

Согласно п. 4.1.1 ТЗ система состоит из публичной части, личного кабинета и админ-панели — без отдельных ролей менеджера/производства. Все три подсистемы работают через общий REST API и одну базу данных, так что цены и коэффициенты, заданные администратором, сразу видны в калькуляторе клиента.

03 · Пользовательские сценарии

Три сквозных пути

Прежде чем рисовать экраны, важно зафиксировать, что именно на них должно происходить.

Гость оформляет заказ без регистрации (п. 3.1, 4.2.3)

flowchart LR
  A["Открывает каталог"] --> B["Выбирает категорию"]
  B --> C["Задаёт параметры"]
  C --> D{"Цена и срок\nпересчитываются\nавтоматически (≤ 1-2 сек)"}

  G --> H["Подтверждает заказ"]
  H --> I["Видит: стоимость предварительная,\nбудет подтверждена после проверки макета"]
  I --> J["Заказ создан со статусом «Новый»"]

Постоянный клиент повторяет прошлый заказ (п. 4.2.3)

  A["Личный кабинет → История заказов"] --> B["Находит прошлый заказ"]

Зачем каждый блок

  • Телефон в шапке виден всегда — часть клиентов малого предприятия всё ещё звонит напрямую.
  • «Как это работает» снимает главный барьер: непонятно, что цену вообще можно узнать не звоня.
  • Карточки популярных категорий = быстрый вход в самый частый сценарий, минуя листание каталога.
  • Вход не обязателен для заказа (п. 4.2.3) — кнопка «Войти» вспомогательная, не блокирующая.

Адаптивность

  • Мобильная версия: hero-текст и фото — в столбец; сетка категорий 4→2 колонки.
  • Меню шапки сворачивается в гамбургер, телефон остаётся виден как иконка-кнопка звонка.

Зачем каждый блок

  • Группы — предложенная категоризация 22 позиций из п. 4.2.1; финальные названия групп утверждает администратор при наполнении.

Адаптивность

  • Сетка карточек: 4 → 2 колонки на планшете → 1–2 на смартфоне.

Подсказка

Итог пересчитывается при каждом изменении параметра, без перезагрузки страницы и без отправки формы.

Логика расчёта на экране (п. 4.2.2)

  • Базовая цена берётся по диапазону тиража (1–50 / 51–200 / >200 шт.).
  • Каждый выбранный параметр умножает/добавляет коэффициент, заданный администратором.
  • Формула: Цена/шт × Тираж + доп. услуги — пересчёт на onChange, без submit.

Почему калькулятор справа и «прилипает»

  • Форма параметров может быть длинной (до 6–8 полей на категорию) — цена должна быть видна всегда, а не только внизу формы.
  • Кнопка перехода к оформлению — прямо под ценой, а не в конце длинной формы.

Адаптивность

  • На мобильном калькулятор превращается в закреплённую снизу панель «Итого: 1560 ₽ · Оформить заказ», а поля формы идут одной колонкой выше.

Обязательное уведомление (п. 4.2.1 ТЗ)

«Предварительная стоимость рассчитана автоматически. Окончательная стоимость будет подтверждена после проверки макета.»

Почему структура именно такая

  • Блок «Ваш заказ» сверху и сворачиваемый — подтверждает клиенту, что параметры не потерялись при переходе со страницы категории; «Изменить параметры» возвращает назад с сохранением выбора.
  • Чекбокс «пришлю позже» — единственный способ отправить заказ без файла (п. 4.2.1); при его выборе зона загрузки скрывается/блокируется.
  • Итоговая карточка справа закреплена (sticky) и видна на всём протяжении прокрутки формы — клиент никогда не теряет из виду сумму.
  • Обязательный дисклеймер о предварительности цены — не тост, который исчезает, а видимый блок рядом с ценой и текст, который останется на экране подтверждения.
  • Вход/регистрация — необязательны и предлагаются мягко, не блокируя отправку (п. 4.2.3: «можно войти без регистрации, чтобы проверить цены»).
  • Согласие на 152-ФЗ — обязательный чекбокс, т.к. форма собирает ФИО, телефон, e-mail (п. 4.1.6).

Надёжность (п. 4.1.4)

  • Черновик формы (параметры + контакты) автосохраняется в браузере при вводе — при случайном закрытии вкладки или обрыве связи данные не теряются.
  • Валидация инлайн: обязательные поля, маска телефона, проверка формата/размера файла — ошибка показывается сразу у поля, без сброса остальной формы.

Экран «Заказ принят» (шаг 3)

  • Номер заказа, статус «Новый», тот же текст о предварительности цены, кнопки «В личный кабинет» и «Вернуться в каталог».

Ключевые элементы

  • Статус — цветной чип, а не только текст, чтобы состояние читалось с одного взгляда по списку из 10+ заказов.
  • «Повторить заказ» ведёт на страницу категории с уже выставленными значениями полей — клиент донастраивает и подтверждает, цена считается по текущему прайсу, а не по цене прошлого заказа.
  • «Загрузить/заменить макет» доступно прямо из деталей заказа — закрывает сценарий «макет пришлю позже» из п. 4.2.1.
  • Пустое состояние (нет заказов): иллюстрация-плейсхолдер + текст «Заказов пока нет» + кнопка «Перейти в каталог».

Адаптивность

  • На мобильном таблица превращается в стопку карточек: одна карточка = один заказ, с тем же чипом статуса.
  • Левое меню — верхние табы вместо боковой колонки.

Экран «Заказы»

  • Табы-счётчики по статусу — администратор один, ему важно сразу видеть, сколько заказов ждёт именно его действия.
  • Открытие заказа — боковая панель, а не отдельная страница: не терять контекст списка при разборе десятков заказов за день.
  • Смена статуса — выпадающий список с 7 фиксированными значениями из п. 4.2.4, без свободного ввода.
  • Каждое изменение цены/статуса пишется в журнал действий (п. 4.1.4) — для разбора спорных ситуаций с клиентом.
